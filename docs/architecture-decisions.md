### 2. D1: 기밀 권한은 샌드박스 단위로 관리한다

기밀 등급이 다른 업무는 샌드박스를 나눈다. 한 샌드박스 안에서 에이전트를 나누는 것은 역할 구분이고 보안 경계가 아니다.

이유:

- 네트워크 정책은 프로그램(바이너리) 단위로 걸린다. 한 샌드박스의 OpenClaw 에이전트들은 같은 프로세스로 돌기 때문에 정책이 에이전트를 구분하지 못한다.
- 파일시스템 정책(Landlock)도 프로세스에 걸린다. 에이전트들은 같은 계정으로 같은 파일을 본다.
- 기억 파일은 샌드박스의 파일시스템에 있다. 샌드박스를 나누면 기억도 함께 나뉜다.

| | 샌드박스를 나눔 | 한 샌드박스 안에서 에이전트를 나눔 |
|---|---|---|
| 설정 파일 | `policies/*.yaml` | `agents/*.yaml` |
| 집행 주체 | OpenShell 프록시와 커널 | OpenClaw 런타임 |
| 파일시스템, 네트워크 정책 | 따로 | 같이 씀 |
| 성격 | 보안 경계 | 역할 구분 |

따라오는 규칙:

- 에이전트 명단은 샌드박스 하나당 파일 하나로 둔다. 모듈별 조각을 하나로 합치지 않는다.
- 외부 입력을 다루는 샌드박스는 `main` 에이전트도 잠근다. `main`은 명단에 없어도 항상 들어가고 기본값이 셸 실행까지 허용이다.

### 3. D2: 추론 제공자는 기밀 등급에 따라 고른다

| 등급 | 제공자 | 프롬프트가 가는 곳 |
|---|---|---|
| 기밀 (회사 내, 사업부 내, 업무 내부) | Ollama (로컬) | 이 PC 밖으로 나가지 않음 |
| 비기밀 (공개) | NVIDIA Endpoints 또는 다른 공개 서비스 | 외부 서버 |

이유: 에이전트가 모델을 호출할 때마다 프롬프트와 도구 결과가 제공자에게 전송된다. 에이전트가 읽은 내부 문서도 프롬프트에 담기면 함께 나간다. 네트워크 정책으로 외부 전송을 막아도 추론 경로는 열려 있으므로, 기밀을 다루는 샌드박스는 추론도 로컬에서 해야 한다.

샌드박스 배정:

| 샌드박스 | 등급 | 제공자 | 모델 |
|---|---|---|---|
| `public` | 공개 | NVIDIA Endpoints | `nvidia/nemotron-3-super-120b-a12b` |
| `team`과 그 밖의 모든 샌드박스 | 회사 내 이상 | Ollama | `qwen3.5:9b` |

외부 제공자에게 보낼 수 있는 것은 공개 등급의 내용뿐이다. 회사 내, 사업부 내, 업무 내부는 서로 등급이 다르지만 외부 제공자 입장에서는 모두 기밀이다. 등급별 배치는 12절에 있다.

2026-09-27 시점의 실제 상태는 목표와 반대다. `my-assistant`가 NVIDIA Endpoints로, `rfa`가 Ollama로 만들어져 있다. 바꾸는 순서는 13절에 적었다.

등급은 샌드박스의 역할 이름이 아니라 **그 샌드박스 안으로 들어오는 데이터**로 정한다.

🔴 **외부 대응 샌드박스(지금의 `rfa`)의 등급은 제안서와 현재 구현(RFA_module `a243c37`)이 서로 다르다.** 그래서 구현을 제안서에 맞추기로 했다 (D10).

| | 제안서 (`proposal.md` 권한 행렬) | 현재 구현 (RFA_module `architecture.md` 3절) |
|---|---|---|
| 외부 대응 쪽이 받는 것 | 승인된 결과물만 | knowledge API의 답변 원문 |
| 기밀 검토가 도는 곳 | 넘어오기 전 (검증 게이트) | `rfa` 안의 `censor_public` 노드 |
| 외부 대응 쪽의 추론 경로 | 승인된 외부 또는 로컬 | 기밀이 프롬프트에 들어가므로 로컬이어야 함 |
| 외부 대응 샌드박스의 등급 | 공개 | 기밀 |

- 현재 구현에서는 knowledge 답변이 걸러지지 않은 채 `rfa`로 들어온다. 데모용 지식에는 미공개 릴리즈 일자와 내부 IP를 일부러 넣어 뒀고, `rfa` 안의 writer, editor, censor가 이 내용을 프롬프트로 받는다.
- 같은 샌드박스의 `public-desk`는 공개 GitHub의 멘션을 읽는다. 외부 입력과 기밀이 한 샌드박스에 함께 있게 된다. 제안서의 경계 규칙("단일 에이전트가 내부 원자료 읽기와 외부 발신을 동시에 가지지 않는다")과 맞지 않는다.
- 게시는 사람 결재 뒤에 호스트 코드가 하므로 게시 경로로는 새지 않는다. 남는 경로는 추론 호출과 `get_thread(target)` 인자다.

검토한 안 (**B로 결정**, 2026-09-27):

| 안 | 내용 | 외부 대응 샌드박스의 등급 | 비용 |
|---|---|---|---|
| A | 현재 구현 유지. 외부 대응 샌드박스를 기밀로 두고 로컬 추론 | 기밀 | 없음. 9B 모델로 작성과 검토를 해야 함 |
| **B (선택)** | 기밀 검토를 지식 제공 쪽으로 옮김. knowledge API는 검토를 통과한 내용만 돌려줌 | 공개 | RFA_module과 knowledge 구현 변경 |
| C | `public-desk`와 워크플로를 다른 샌드박스로 나눔 | 입구는 공개, 워크플로는 기밀 | 샌드박스 하나 추가 |

🔴 **현재 구성으로는 D2가 지켜지지 않는다.** OpenShell은 gateway 하나에 추론 경로를 하나만 둔다. 같은 gateway의 샌드박스들은 그 경로를 번갈아 쓴다.

- NemoClaw 문서: "OpenShell exposes one live inference route per gateway."
- 확인(2026-09-27): `openshell inference get`의 결과가 `ollama-local` / `qwen3.5:9b`였다. `rfa` 온보딩이 경로를 바꾼 것이다. 이 상태에서 `my-assistant`가 `inference.local`을 호출하자 `inference service unavailable`이 돌아왔다.
- 반대 방향이 더 위험하다. 어느 샌드박스에서든 `connect`나 `inference set`으로 경로를 NVIDIA Endpoints로 바꾸면, 같은 gateway에 있는 기밀 샌드박스의 프롬프트도 그 순간부터 외부로 나간다.

샌드박스의 `openclaw.json`에 적힌 모델 이름은 실제로 어디로 가는지를 정하지 않는다. 실제 목적지는 gateway의 경로가 정한다.

### 4. D3: 기밀 등급마다 gateway를 따로 둔다 (제안)

D2를 지키려면 기밀 샌드박스와 공개 샌드박스가 서로 다른 gateway를 써야 한다. 제공자가 둘이므로 gateway도 둘이면 된다. 등급 수만큼 필요한 것은 아니다.

| gateway | 포트 | 등록할 제공자 | 샌드박스 |
|---|---|---|---|
| 공개용 | 8080 (지금 것) | NVIDIA Endpoints | `public` |
| 기밀용 | 8090 (새로 만듦) | Ollama만 | `team`. 나중에 `company`, `division` |

기밀용 gateway에는 외부 제공자의 API 키를 등록하지 않는다. 경로를 실수로 바꾸더라도 외부로 보낼 자격증명이 없으므로 기밀 프롬프트가 나갈 수 없다.

```bash
NEMOCLAW_GATEWAY_PORT=8090 nemoclaw onboard --name team --agents agents/team.yaml --no-gpu --control-ui-port 18791
```

- 기본이 아닌 포트를 쓰면 상태가 `~/.nemoclaw/gateways/<포트>/`에 따로 저장된다. 샌드박스 목록도 따로다.
- `NEMOCLAW_GATEWAY_PORT`는 온보딩할 때만 gateway를 고른다. 이미 만든 샌드박스의 명령은 기록된 gateway로 간다.

미검증: 이 PC(WSL2, Docker Desktop)에서 gateway를 두 개 띄워 보지 않았다. 메모리 사용량과 포트 충돌 여부를 확인해야 한다. `agents/team.yaml`은 초안이고 샌드박스에 구워 보지 않았다.

gateway를 나누지 않는 대안:

| 대안 | 결과 |
|---|---|
| 모든 샌드박스를 Ollama로 | D2는 지켜짐. 외부 대응 글의 품질이 떨어짐 |
| 모든 샌드박스를 NVIDIA Endpoints로 | 동작은 확실함. 기밀 프롬프트가 외부로 나감 |

### 5. D4: 샌드박스끼리는 호스트 서비스 API로만 주고받는다

샌드박스는 서로 직접 말하지 않는다. 호스트에 띄운 서비스(review `:8790`, knowledge `:8791`)의 API를 거치고, 어느 경로를 열지는 네트워크 정책이 정한다.

- 호스트 서비스 주소는 IP 리터럴로 적는다. `host.docker.internal`, `host.openshell.internal`은 정책에 넣지 않는다. 이 이름으로 들어온 요청은 호스트에서 `127.0.0.1` 출처로 보인다.
- 허용 프로그램은 python뿐이다. curl은 검증할 때만 임시로 연다.

비서가 다른 샌드박스의 에이전트에게 일을 넘기는 `subagents.allowAgents` 경로는 샌드박스가 다르면 쓸 수 없다. API 호출로 대신한다.

### 6. D5: 사람 결재 경로는 에이전트가 호출할 수 없다

`/reviews/*/approve`, `/reviews/*/reject`, `/reviews/*/republish`, `POST /policy/**`는 `deny_rules`로 명시해서 막는다. allow 목록에 없어서 이미 막히지만, 나중에 allow가 넓어져도 막히도록 따로 적는다.

이 환경에서 샌드박스의 승인 호출을 막는 것은 네트워크 정책 하나다. review 서비스의 출처 주소 검사는 Docker Desktop에서 우회되는 것을 확인했다. 승인용 토큰으로 바꾸는 안은 팀 확인이 필요하다.

### 7. D6: 네트워크 정책은 Restricted에서 시작한다

| 샌드박스 | tier | 추가로 여는 것 |
|---|---|---|
| `public` | Restricted | `rfa-host-services` |
| `team` | Restricted | `local-inference`와 이 샌드박스가 부를 호스트 서비스 |
| `my-assistant` (정리 예정) | Balanced | `npm`, `pypi`, `huggingface`, `brew`, `openclaw-pricing` |

- 네트워크 정책은 샌드박스를 다시 만들지 않고 바꿀 수 있다 (`nemoclaw <이름> policy add/remove`). 좁게 시작해도 부담이 없다.
- `github` 프리셋은 켜지 않는다. GitHub는 호스트의 MCP 서버를 거친다. 프리셋을 켜면 샌드박스가 GitHub에 직접 나간다.
- 워크플로 의존성을 설치할 때만 `pypi`를 잠깐 켠다.

`rfa-host-services`는 정책 이름이고 샌드박스 이름이 아니다. 외부게시 모듈(RFA_module)의 호스트 서비스로 가는 경로를 뜻하므로 그대로 둔다. 지금은 검증하느라 `my-assistant`에 임시로 붙어 있다.

### 8. D7: 로컬 추론의 운영 조건

| 항목 | 값 |
|---|---|
| 모델 | `qwen3.5:9b` (9.7B, Q4_K_M, 6.6GB) |
| context | 8192 |
| 동시 처리 | 하지 않음. 요청은 차례로 처리 |
| 실행 위치 | 호스트(WSL)의 `ollama serve`. 컨테이너가 아님 |

이 PC(RTX 4060 8GB, RAM 16GB, 20코어)에서 측정한 값 (2026-09-27):

| context | 모델 크기 | 올라간 위치 | 프롬프트 5,912토큰 처리 | 생성 속도 |
|---|---|---|---|---|
| 4096 | 5.5GB | 100% GPU | 측정 안 함 | 측정 안 함 |
| 8192 | 5.6GB | 100% GPU | 2.9초 | 41 tok/s |
| 16384 | 6.6GB | GPU 84% / CPU 16% | 3.5초 | 32 tok/s |
| 32768 | 7.2GB | GPU 76% / CPU 24% | 측정 안 함 | 측정 안 함 |

- 8192는 전부 GPU에 올라가는 가장 큰 값이다.
- Ollama 기본값은 4096이다. NemoClaw는 Ollama가 보고하는 값을 OpenClaw의 `contextWindow`로 쓰므로, 온보딩 전에 Ollama를 8192로 띄워야 한다.
- 에이전트 수는 메모리에 영향을 주지 않는다. 모델 하나를 같이 쓴다.
- 샌드박스 하나는 RAM 0.5~0.9GB를 쓴다.

```bash
pkill -f 'ollama serve'
OLLAMA_CONTEXT_LENGTH=8192 ollama serve &
```

미검증: 8192가 `public-desk`의 시스템 프롬프트와 MCP 도구 정의를 담기에 충분한지, 9B 모델이 도구를 정확히 호출하는지, 기밀 검토 판단의 품질. 짧은 응답으로 한 번씩만 측정했다.

### 9. D8: 샌드박스에 GPU를 넘기지 않는다

- 비기밀 샌드박스는 추론을 외부 API로 하므로 GPU가 필요 없다.
- 기밀 샌드박스가 쓰는 Ollama는 호스트에서 돌며 GPU를 직접 쓴다. 컨테이너에 GPU를 넘길 필요가 없다.
- GPU passthrough를 켜면 온보딩이 `CapAdd` 오류로 실패했다.

`nemoclaw onboard`에는 매번 `--no-gpu`를 붙인다. 세션에 저장되지 않는다.

### 10. D9: 웹 검색과 메시징 채널은 켜지 않는다

- 승인과 게시 흐름에 웹 검색이 필요하지 않다. 켜면 외부로 나가는 경로가 늘어난다.
- Brave Search는 카드 등록이 필수이고 무료분을 넘으면 과금된다. 필요해지면 Tavily를 쓴다.
- NemoClaw의 메시징 채널은 사람이 에이전트와 대화하는 입구다. 이 제품의 게시 채널(결과물이 나가는 목적지)과는 다른 것이다. 알림과 결재는 자체 UI가 맡는다.

### 11. D10: 기밀 검토는 등급 경계를 넘기 전에 한다

데이터는 높은 등급에서 낮은 등급으로 넘어가기 **전에** 검토를 받는다. 낮은 등급의 샌드박스는 검토를 통과한 내용만 받는다.

```
team (업무 내부)                            public (공개)
  업무 에이전트 → 답변 원문
  기밀 검토 에이전트 → 공개용으로 걸러낸 답변  ──(호스트 API)──▶  외부 대응 에이전트 → 초안
                                                                  │
                                              호스트: 스캐너 → 사람 결재 → 게시
```

- 기밀 검토 에이전트는 원문과 기밀 기준을 읽어야 한다. 기밀 기준 자체가 기밀이므로(예: 차기 버전 릴리즈 일자, 외부에 알리고 싶지 않은 GPU pool) 검토는 높은 등급 쪽에서 돈다.
- 외부 대응 샌드박스에는 기밀이 들어오지 않는다. 악의적인 외부 입력이 들어와도 빼낼 것이 없다. 제안서의 경계 규칙("단일 에이전트가 내부 원자료 읽기와 외부 발신을 동시에 가지지 않는다")과 맞는다.
- 호스트의 스캐너와 사람 결재는 그대로 둔다. 기밀 검토가 놓친 것을 잡는 두 번째 관문이다.

필요한 변경 (팀 확인 전):

| 대상 | 변경 | 담당 |
|---|---|---|
| knowledge API | 요청에 독자 범위를 받고, 그 범위에 맞게 걸러낸 답변만 돌려줌 | 민섭 님 |
| RFA_module 워크플로 | `censor_public`, `censor_internal` 노드를 `public`에서 빼고 `team` 쪽으로 옮김 | 승희 님 |
| 기밀 기준 문서, 피드백 | `public`이 읽지 않게 함 (`GET /policy/*` 허용 제거) | 다영 |
| 데모용 지식 | 미공개 일자와 내부 IP는 그대로 둠. 걸러지는 위치만 바뀜 | 승희 님 |

### 12. D11: 기밀 등급 4단계와 샌드박스 배치

팀이 처음 적은 구조에서 독자 범위는 네 가지다.

| 등급 | 독자 | 나가는 곳 | 외부 추론 |
|---|---|---|---|
| 공개 | 인터넷 | 공개 GitHub, 외부 문의 회신 | 가능 |
| 회사 내 | 회사 구성원 | 사내 기술 블로그, 제품팀 Q&A | 불가 |
| 사업부 내 | 사업부 구성원 | 사업부 Confluence | 불가 |
| 업무 내부 | 업무 담당자 | 없음. 원자료와 기억 | 불가 |

등급이 아닌 것:

- **대외적 기밀과 개인적 기밀**은 검토 기준의 종류다. 기밀 검토 에이전트가 쓰는 규칙이고, 샌드박스를 나누는 기준이 아니다.
- **업무 3개(ORBIT 벤치마크, 양자화 조사, PRISM 개발)**는 같은 등급 안의 구획이다. 서로의 기억을 보면 안 된다면 업무 내부 샌드박스를 셋으로 나눈다.

에이전트는 자기가 읽는 데이터 중 가장 높은 등급의 샌드박스에 둔다.

| 샌드박스 | 등급 | 에이전트 | 제공자 | gateway | 첫 구현 |
|---|---|---|---|---|---|
| `public` | 공개 | Public 대응 (`public-desk`), 작성, 편집 | NVIDIA Endpoints | 공개용 (8080) | 만듦 |
| `company` | 회사 내 | Internal 대응 (제품팀 Q&A), 사내 기술 블로그 게시 | Ollama | 기밀용 (8090) | 뺌 |
| `division` | 사업부 내 | 사업부 Confluence 게시 | Ollama | 기밀용 (8090) | 뺌 |
| `team` | 업무 내부 | 비서, 기밀 검토, 업무 에이전트 | Ollama | 기밀용 (8090) | 만듦 |

- 비서는 업무 지식을 바탕으로 초안을 만든다. 업무 내부 등급에 둔다.
- 제품팀 Q&A를 회사 내로 본 것은 가정이다. 제품팀이 같은 사업부라면 사업부 내가 된다.
- 샌드박스 하나는 RAM 0.5~0.9GB를 쓴다. 이 PC(16GB)에서 네 개를 모두 띄울 수 있다. 직접 띄워 보지는 않았다.

### 13. D12, D13: 이름 규칙과 첫 구현 범위

**D12. 샌드박스 이름은 기밀 등급을 따른다.** 등급은 독자 범위로 부른다.

| 등급 | 샌드박스 이름 | 에이전트 명단 |
|---|---|---|
| 공개 | `public` | `agents/public.yaml` |
| 회사 내 | `company` | `agents/company.yaml` (아직 없음) |
| 사업부 내 | `division` | `agents/division.yaml` (아직 없음) |
| 업무 내부 | `team` | `agents/team.yaml` (초안) |

- 같은 등급 안에서 구획을 나눌 때는 뒤에 붙인다. 예: `team-orbit`, `team-prism`.
- 이름만 보고 그 샌드박스에 무엇을 넣어도 되는지 알 수 있다. 모듈이나 담당자 이름을 쓰면 모듈이 늘 때마다 등급을 따로 기억해야 한다.
- NemoClaw의 이름 규칙: 1~19자, 소문자로 시작, 소문자와 숫자와 하이픈만.
- 정책 이름(`rfa-host-services`)과 모듈 이름(RFA_module)은 바꾸지 않는다. 등급이 아니라 대상 서비스를 가리킨다.

**D13. 첫 구현은 공개와 업무 내부 두 등급만 만든다.** 회사 내와 사업부 내는 구조와 확장 경로로만 둔다.

- 실제로 연동하는 채널이 공개 GitHub 하나다.
- 두 등급이면 "기밀이 있는 곳"과 "외부와 닿는 곳"의 분리를 보여줄 수 있다. 가운데 두 등급은 같은 방식으로 끼워 넣으면 된다.
- 첫 구현에서 빠지는 에이전트: Internal 대응(제품팀 Q&A), 기밀 검토 Internal, 사내 채널 게시.

등급을 추가할 때 하는 일:

| 순서 | 일 |
|---|---|
| 1 | `agents/<등급>.yaml` 작성 |
| 2 | 기밀용 gateway에 `nemoclaw onboard --name <등급>` |
| 3 | 그 등급이 부를 호스트 서비스의 정책 파일 작성과 적용 |
| 4 | `team`의 기밀 검토 에이전트에 그 등급용 검토 기준 추가 |
| 5 | knowledge API가 그 독자 범위를 받도록 확장 |

현재 상태 (2026-09-27)와 옮기는 순서:

| 떠 있는 샌드박스 | 제공자 | gateway | 목표 |
|---|---|---|---|
| `rfa` | Ollama | 8080 | `public`으로 다시 만들고 NVIDIA Endpoints로 |
| `my-assistant` | NVIDIA Endpoints (기록상) | 8080 | 비서를 `team`으로 옮기고 정리 |

| 순서 | 일 | 명령 또는 비고 |
|---|---|---|
| 1 | 기밀용 gateway(8090)에 `team` 생성 | Ollama를 context 8192로 먼저 띄움 |
| 2 | `rfa`를 지우고 `public`으로 다시 생성 | `nemoclaw rfa destroy`, `nemoclaw onboard --name public --agents agents/public.yaml --no-gpu` |
| 3 | `public`에 정책 적용. `GET /policy/*` 허용은 제거 | `scripts/apply_policies.sh public --apply` |
| 4 | `my-assistant` 정리 | `nemoclaw my-assistant destroy` |

2번에서 `public`의 제공자를 NVIDIA Endpoints로 고르면 gateway 8080의 경로가 외부로 바뀐다. D10의 변경이 끝나기 전에는 knowledge 답변에 기밀이 그대로 들어 있으므로, 그 전에 `public`에서 워크플로를 돌리면 기밀이 외부로 나간다.
