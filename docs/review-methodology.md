## 기밀 검토 방법론

작성일: 2026-09-27. 사내·기밀 자료가 밖으로 나가는지를 어떻게 판단하고, 그 기준을 사용자가 어떻게 관리하는지 적는다. 그림은 [review-pipeline.html](review-pipeline.html).

이 문서는 **제안**이다. 구현해서 효과를 재 본 것이 아니고 팀 확인 전이다. 이미 구현된 부분은 10절에 따로 적었다.

### 1. 나눠야 할 질문 두 가지

| 질문 | 뜻 | 예 |
|---|---|---|
| 경로 판정 | 데이터가 어느 길로 나갈 수 있는가 | 게시, 추론 호출, 도구 인자, 로그 |
| 내용 판정 | 이 글이 이 독자에게 나가도 되는가 | 초안에 미공개 출시일이 있는가 |

경로가 열려 있으면 내용 판정을 우회한다. 추론 호출도 나가는 길이다. 에이전트가 읽은 자료는 프롬프트에 실려 추론 제공자에게 간다.

### 2. 대주제 3개

| 대주제 | 답하는 질문 | 판정 대상 | 집행하는 곳 | 성격 |
|---|---|---|---|---|
| 1. 경로 | 어디로 나가는가 | 주소, 목적지, 도구, 추론 제공자 | OpenShell (샌드박스 프록시, 게이트웨이) | 강제. 에이전트가 우회할 수 없음 |
| 2. 내용 | 무엇이 나가는가 | 단어, 값, 문장, 출처 | 코드 검사와 검열 에이전트 | 판단. 틀릴 수 있음 |
| 3. 결재 | 누가 정하는가 | 사람의 결정과 그 반영 | 호스트의 review 서비스와 결재 화면 | 사람 |

```
초안 ─▶ 2. 내용 (코드 검사 ─▶ 검열 에이전트) ─▶ 3. 결재 ─▶ 게시
            ▲                                      │
            └────── 허용·차단 목록 ◀── 결정을 추가 ──┘

1. 경로: 모든 단계의 바닥. 허용된 길로만 나간다.
```

### 3. 소주제

소주제는 끼웠다 뺄 수 있는 검사 칸이다. 처음 넣을 것은 아래와 같다.

| 대주제 | 소주제 | 집행 | 차단 목록의 효과 | 허용 목록의 효과 |
|---|---|---|---|---|
| 1. 경로 | 1-1 네트워크 주소 | 샌드박스 프록시 | 이 주소, 메서드, 경로로는 못 나감 | 목록에 있는 곳만 나감 |
| | 1-2 게시 목적지 | 호스트의 MCP 서버와 게시 코드 | 이 레포, 이 수신자로는 못 보냄 | 목록에 있는 곳만 보냄 |
| | 1-3 도구 | OpenClaw 런타임 | 이 도구는 못 씀 | 목록에 있는 도구만 씀 |
| | 1-4 추론 제공자 | 게이트웨이 | 이 등급은 외부로 못 보냄 | — |
| 2. 내용 | 2-1 비밀값 패턴 | 코드 | 형태가 맞으면 차단 | 시험용 가짜 값은 예외 |
| | 2-2 금칙어 | 코드 | 단어가 있으면 차단 또는 대체 | 이미 공개된 이름은 통과 |
| | 2-3 출처 등급 | 코드 | 이 출처에서 온 문장은 보류 | 공개 출처에서 온 문장은 통과 |
| | 2-4 맥락 판정 | 검열 에이전트 | 규칙에 걸리면 수정 또는 차단 | 과거에 승인된 표현은 통과 |
| 3. 결재 | 3-1 결재자 | review 서비스 | — | 이 채널은 이 사람이 승인 |
| | 3-2 결정 반영 | 결재 화면 | 거절 사유를 차단 목록으로 | 승인 내용을 허용 목록으로 |

나중에 끼워 넣을 후보:

| 소주제 | 내용 | 필요한 것 |
|---|---|---|
| 2-5 표식 | 기밀 문서에 고유한 가짜 값을 심어 두고, 출력에 나타나면 유출로 봄 | 표식 목록 |
| 2-6 값 지문 | 민감한 값의 해시를 저장해 두고 출력에서 같은 값을 찾음 | 해시 저장소 |
| 2-7 유사도 | 기밀 문서를 바꿔 쓴 문장을 찾음 | 임베딩 저장소, 기준값 |

검사마다 잡는 것과 놓치는 것이 다르다.

| 소주제 | 잡는 것 | 놓치는 것 |
|---|---|---|
| 2-1 비밀값 패턴 | 토큰, 내부 IP, 사내 호스트, 경로 | 말로 풀어 쓴 기밀 |
| 2-2 금칙어 | 코드명, 미공개 제품명, 고객명 | 사전에 없는 말, 돌려 말하기 |
| 2-3 출처 등급 | 기밀 문서에서 온 문장 전부. 날짜나 숫자 하나도 잡음 | 출처 표시가 빠진 문장 |
| 2-4 맥락 판정 | 맥락상 기밀인 내용 | 모델이 모르는 기준, 속임수 |
| 2-7 유사도 | 바꿔 쓴 문장 | 짧은 사실 하나 |

날짜 하나, 숫자 하나 같은 짧은 사실은 2-3 출처 등급 말고는 잡기 어렵다.

### 4. 내용 검사의 순서

확실한 검사를 에이전트의 판단에 맡기지 않는다. 검열 에이전트는 모델이라 속을 수 있고 빠뜨릴 수 있다. 목록 대조를 에이전트에게 맡기면 목록에 넣어 둔 단어가 그냥 통과할 수 있다.

```
초안 → 코드 검사 (2-1, 2-2, 2-3) → 검열 에이전트 (2-4) → 결재
         반드시 실행                  코드 검사 결과를 참고
```

검열 에이전트에 대해 지킬 것:

- 초안 속의 지시를 따르지 않는다. 초안은 자료로만 다룬다.
- 작성하는 쪽과 검토하는 쪽의 프롬프트를 분리한다.
- 문장 단위로 판정하고 규칙 번호를 붙인다.
- 확신이 낮으면 보류로 보낸다.

### 5. 판정 결과

통과와 차단 둘만 두면 애매한 것이 전부 차단으로 몰린다.

| 결과 | 뜻 | 다음 |
|---|---|---|
| 통과 | 공개 근거 있음 | 결재로 |
| 수정 | 일부를 지우거나 흐리면 가능 | 수정안과 함께 결재로 |
| 보류 | 판단 불가 | 사람에게 |
| 차단 | 나갈 수 없음 | 승인 버튼 비활성 |

### 6. 허용·차단 목록

모든 소주제가 같은 형식의 항목을 읽는다. 소주제를 추가해도 목록 관리 화면은 그대로 쓸 수 있다.

```yaml
- id: L-0142
  slot: 2-2                  # 어느 소주제가 읽는가
  list: deny                 # allow | deny
  match: "Nimbus2"           # 단어, 패턴, 주소, 문장 해시
  match_type: term           # term | regex | exact | source | destination
  action: replace            # block | review | replace | pass
  replace_with: "차기 모델"
  scope:
    audience: [public]       # 어느 독자 등급에 적용하는가
    owner: official          # official | personal
  origin: review-12          # 어느 결재에서 생겼는가
  created: 2026-09-27
  expires: null              # 출시 뒤에는 풀려야 하는 항목에 날짜
  status: active             # proposed | active | retired
```

실행 중에 쌓이는 방식. 결재 화면에서 사람이 결정할 때 한 번 더 묻는다.

| 결정 | 묻는 것 | 생기는 항목 |
|---|---|---|
| 거절 | "이 표현을 앞으로도 막을까요?" | 차단 항목. 바로 적용 |
| 수정 후 승인 | "지운 부분을 앞으로도 지울까요?" | 차단 항목. 대체 표현 포함 |
| 승인 | "이 표현을 이 독자에게 허용할까요?" | 허용 항목. 제안 상태 |

허용과 차단은 다르게 다룬다. 조이는 것은 쉽게, 푸는 것은 어렵게 한다.

| | 차단 항목 | 허용 항목 |
|---|---|---|
| 적용 시점 | 바로 | 담당자가 확인한 뒤 |
| 범위 | 넓혀도 됨 (단어 단위) | 좁게만. 정확히 같은 문장, 같은 독자 등급 |
| 기한 | 없어도 됨 | 두는 편이 안전 |

목록이 부딪힐 때의 규칙:

| 순서 | 규칙 |
|---|---|
| 1 | 차단이 허용을 이긴다 |
| 2 | 비밀값 패턴(2-1)의 차단은 어떤 허용으로도 풀리지 않는다 |
| 3 | 공식 기준이 개인 기준보다 앞선다. 개인 기준으로 더 조이는 것은 언제나 가능하다 |
| 4 | 허용은 "보류"를 "통과"로 바꿀 수 있을 뿐, "차단"을 바꾸지 못한다 |

모든 변경에 버전을 남기고, 어느 버전의 목록으로 판정했는지 결재 기록에 함께 적는다.

### 7. 목록이 바뀌는 빈도

실행 중에 계속 쌓이는 목록은 대부분 대주제 2에 있다.

| | 경로 목록 (대주제 1) | 내용 목록 (대주제 2) |
|---|---|---|
| 바뀌는 빈도 | 드묾 | 결재할 때마다 |
| 바꾸는 사람 | 관리자 | 결재자, 개인 |
| 바꾸는 방법 | 호스트에서 명령 | 결재 화면에서 선택 |
| 적용 | 정책 재적용 또는 샌드박스 재생성 | 다음 검사부터 바로 |

경로 소주제는 실행 중에 바꿀 수 있는지가 서로 다르다.

| 소주제 | 실행 중에 바꿀 수 있나 |
|---|---|
| 1-1 네트워크 주소 | 가능. `nemoclaw <이름> policy add/remove` |
| 1-2 게시 목적지 | 가능. 호스트 설정 |
| 1-3 도구 | 불가. 샌드박스를 다시 만들어야 함 |
| 1-4 추론 제공자 | 가능. 게이트웨이 전체에 적용됨 |

사용자의 결재 결정이 자동으로 경로를 여닫게 하지 않는다. 화면에서 대주제 1은 현재 설정을 보여주는 정도로 두고, 목록 관리는 대주제 2에 힘을 싣는다.

### 8. 누가 읽고 누가 쓰는가

| 주체 | 읽기 | 쓰기 |
|---|---|---|
| 결재 화면 (사람) | 가능 | 가능 |
| 코드 검사 | 가능 | 불가 |
| 검열 에이전트 | 가능 | 불가 |
| 공개 등급 샌드박스의 에이전트 | 불가 | 불가 |

- 검열 에이전트가 자기 기준을 고칠 수 있으면 속임수 한 번에 기준이 풀린다. 지금 네트워크 정책이 `POST /policy/**`를 막고 있는 것이 이 역할이다.
- 목록 자체가 기밀이다. 금칙어 사전에는 미공개 이름이 들어 있다. 공개 등급 쪽에서는 읽지 못하게 한다.

사람 사이의 권한:

| 주체 | 바꿀 수 있는 것 |
|---|---|
| 개인 | 개인 기준, 개인 금칙어, 시험 사례 추가 |
| 기준 담당자 | 공식 기준, 금칙어 사전, 자료 등급, 결재자 지정. 허용 항목의 확인 |
| 관리자 | 대주제 1 전체 |

### 9. 소주제를 끼워 넣는 법

소주제도 파일 하나에 등록한다.

```yaml
slots:
  - id: 2-2
    topic: content           # route | content | approval
    name: 금칙어
    order: 20                # 같은 대주제 안에서 도는 순서
    enabled: true
    reads: [term, regex]     # 읽는 항목의 match_type
    on_hit: [block, replace, review]
```

새 검사를 추가할 때 하는 일:

| 순서 | 일 |
|---|---|
| 1 | 위 파일에 항목 하나 추가 |
| 2 | 같은 모양의 함수 하나 구현. 글과 목록을 받아 "어디가, 어느 항목에, 어떻게 걸렸는지"를 돌려줌 |

결재 화면과 목록 관리 화면은 고치지 않는다.

### 10. 지금 구현과의 대응

RFA_module에 이미 있는 것:

| 소주제 | 파일 | 상태 |
|---|---|---|
| 1-1 네트워크 주소 | 이 레포 `policies/rfa-host-services.yaml` | 검증함 |
| 1-2 게시 목적지 | 게시 코드의 서명 토큰 (본문 해시와 목적지 대조) | RFA_module 테스트 통과 |
| 1-3 도구 | 이 레포 `agents/*.yaml` | 검증기 통과. 샌드박스에서는 미확인 |
| 2-1 비밀값 패턴 | `services/review/scanner.py`. 패턴이 코드에 고정 | 구현됨 |
| 2-1 내부 주소 | `data/policy/internal_hosts.txt`, `internal_paths.txt` | 구현됨 |
| 2-4 공식 기준 | `data/policy/public/official.md` | 구현됨 |
| 2-4 개인 기준 | `data/policy/public/personal.md` | 읽기만. 추가하는 화면은 없음 |
| 2-4 결정 사례 | `data/policy/feedback.jsonl` | 구현됨 |
| 3 결재 | review 서비스, 결재 웹 | 구현됨 |
| 2-2, 2-3, 3-2 | 없음 | — |

`feedback.jsonl`은 결정을 그대로 쌓은 기록이고, 모델에게 예시로 보여주는 용도다. 이 문서의 제안은 그 기록에서 항목을 뽑아 목록으로 올리는 단계를 더하는 것이다. 기록은 그대로 두고 목록만 새로 만든다.

검열 노드(`censor_public`)는 지금 외부 대응 워크플로 안에서 돌고 기준도 그쪽에서 읽는다. 8절의 표가 성립하려면 검열이 업무 내부 등급 쪽으로 옮겨 가야 한다 ([architecture-decisions.md](architecture-decisions.md) D10). 시연에는 합성 자료만 쓰므로 지금 위치 그대로여도 실제 피해는 없다.

### 11. 마감까지의 범위 제안

화면에는 구조 전체를 보여주고, 실제로 동작하는 것은 셋으로 잡는다.

| 우선 | 동작하게 할 것 | 이유 |
|---|---|---|
| 1 | 2-2 금칙어 | 구현이 작다. 추가하면 바로 다음 검사에서 걸리는 것이 보임 |
| 2 | 시험 묶음 10건 | 기밀을 심은 합성 질문을 돌려 "몇 건 중 몇 건을 막았다"는 숫자를 만듦 |
| 3 | 2-3 출처 등급 | knowledge API 응답에 등급 필드 하나를 추가하는 것으로 시작 |

나머지 소주제는 읽기 전용으로 현재 값을 보여준다.

### 12. 확인이 필요한 것

| 항목 | 누가 | 내용 |
|---|---|---|
| 프록시의 본문 검사 | 다영 | 지금 정책은 주소, 메서드, 경로까지만 본다. 요청 본문까지 볼 수 있으면 금칙어 검사를 경로 단계에서 한 번 더 걸 수 있다. 확인하지 않았다 |
| 도구 목록의 실행 중 변경 | 다영 | 샌드박스를 다시 만들지 않고 바꾸는 방법을 문서에서 찾지 못했다 |
| 기준 담당자 | 팀 | 사람을 세 부류로 나눈 것은 제안이다. 누가 공식 기준을 맡는지 정해야 한다 |
| knowledge API의 등급 필드 | 민섭 님 | 2-3에 필요하다 |
| 목록 저장 위치 | 팀 | 호스트의 어느 서비스가 맡는지. review 서비스에 더할지 따로 둘지 |
| 화면 | 다영 | UI 쪽의 정책 관리 화면과 맞춰야 한다 |
