## 마일스톤과 세부 계획

고친 날: 2026-09-27 17:00. 제출 마감: 2026-09-28 23:59. 팀 미팅: 2026-09-27 저녁.

상태 표기: ✅ 끝남 · 🔶 진행 중 · ⬜ 시작 전 · ⛔ 막힘

구조는 [architecture-decisions.md](architecture-decisions.md) 15절(D15~D18)을 따른다. 2026-09-27 오후에 구조가 바뀌어 이 문서를 다시 썼다.

| 바뀐 것 | 이전 | 지금 |
|---|---|---|
| 샌드박스 | 공개 쪽 `public`과 기밀 쪽 `team` | 기밀 영역의 `team` 하나 |
| 대응 에이전트 | 업무마다 하나. 샌드박스 안 | 하나. 샌드박스 없이 호스트에서 |
| 사람의 검사 | 게시 직전에 초안을 봄 | 경계를 넘기 전에 지식을 봄 |
| 가장 큰 일 | 샌드박스 안에서 워크플로 실행 | 기밀 영역의 검열과 기밀 검사 |

### 1. 목표

> 채널에서 질문이 들어오면 기밀 영역의 에이전트가 답을 만들고, 검열 에이전트가 거른 것을 사람이 검사한 뒤에만 밖으로 나간다. 기밀을 읽는 에이전트는 샌드박스 안에 있고, 허용된 길 말고는 밖으로 나갈 수 없다는 것을 보여준다.

시연에서 보여줄 장면:

1. 정상 흐름. 질문 → 기밀 영역에서 답변 → 검열 → 사람의 기밀 검사 → 대응 에이전트가 다듬음 → 게시
2. 기밀 차단. 원문에 섞인 미공개 일정과 비밀값이 기밀 검사 화면에서 걸러지는 것이 보임
3. 공격 차단. 기밀 영역의 에이전트가 허용 안 된 곳으로 보내려는 시도가 샌드박스에서 막히고 로그로 남음

시연에는 합성 자료만 넣는다. 추론이 외부 API로 나간다 (D14).

| M2 | 네트워크 정책을 쓰는 법 | 허용과 차단이 경로 단위로 갈리는 것을 확인 | ✅ 옛 샌드박스에서 확인 |
| M3 | 기밀 영역 샌드박스 `team` | 명단과 정책이 적용된 `team`이 Ready, 도구 제한 확인 | ⬜ |
| M4 | 기밀 검사 | 검열 에이전트가 올린 것을 사람이 승인하면 승인된 지식이 API로 나옴 | ⬜ 가장 큰 일 |
| M5 | 연결 | 질문 1건이 기밀 영역, 기밀 검사, 대응 에이전트를 거쳐 게시까지 한 바퀴 | ⬜ |

핵심 경로는 M3 → M4 → M5다. M1은 승희 님 쪽에서 이미 호스트 실행까지 되어 있어서, 남은 위험은 기밀 영역 쪽에 몰려 있다.

### 3. 지금 상태

- 샌드박스: 옛 이름인 `my-assistant`와 `rfa`로 만들어 봤다. `team`은 아직 없다. 상태는 `nemoclaw list`로 확인한다.
- 호스트 서비스: review(8790), knowledge(8791)가 실행 중이었다.
- RFA_module: `main`이 Step 9(호스트 실행)까지 왔다. PR #12(샌드박스 안에서 실행)와 PR #13(OpenAI 방식 추가)이 열려 있다.
- 이 레포: `agents/team.yaml`은 초안이다. `team`용 네트워크 정책은 없다. 검열 에이전트와 기밀 검사 화면은 없다.

남은 시간이 하루 남짓이라 어디까지 할지를 먼저 정한다.

| 범위 | 내용 | 시연에서 보이는 것 |
|---|---|---|
| 최소 | M3 `team` 샌드박스와 차단 장면. M1은 지금의 RFA_module 그대로. 검열과 승인은 흉내(이미 승인된 지식을 돌려줌) | 정상 흐름, 공격 차단. 기밀 차단은 화면 시안으로 |
| 목표 | 최소 + M4. 검열 에이전트가 실제로 거르고, 사람이 기밀 검사 화면에서 승인 | 세 장면 모두 |
| 여유 | 목표 + 허용·차단 목록이 결정에서 쌓임, 금칙어 검사 | 목록에 추가하면 다음 검사에서 걸리는 장면 |

9/28 12:00에 M4가 돌지 않으면 최소 범위로 내려간다.

### 5. M3 세부 계획: 기밀 영역 샌드박스 `team`

| # | 할 일 | 끝났다는 기준 | 상태 |
|---|---|---|---|
| 3-1 | 추론 경로 확인 | `openshell inference get`이 NVIDIA Endpoints | ⬜ |
| 3-2 | `team` 온보딩 | `nemoclaw list`에 `team`, 미완료 표시 없음 | ⬜ |
| 3-3 | 에이전트 명단 반영 확인 | `nemoclaw team agents list`에 `main`, `task-orbit`, `censor-public` | ⬜ |
| 3-4 | `team`이 부를 호스트 주소 정하기 | 질문 받기와 검열 결과 올리기의 주소와 메서드가 정해짐 | ⬜ 팀 확인 |
| 3-5 | `team`용 네트워크 정책 작성과 적용 | 3-4의 주소만 열림 | ⬜ |
| 3-6 | 정책 검증 | 허용된 주소는 통과, 승인 주소와 그 밖의 주소는 차단 | ⬜ |
| 3-7 | 도구 제한 검증 | 에이전트에게 셸 실행을 시켰을 때 도구가 없어 못 함 | ⬜ |
| 3-8 | 옛 샌드박스 정리 | `rfa`, `my-assistant` 삭제 | ⬜ |

```bash
source ~/.secrets/nvidia.env
openshell inference get
nemoclaw onboard --name team --agents agents/team.yaml --no-gpu
nemoclaw team agents list
RFA_HOST_IP=<호스트 IP> ./scripts/apply_policies.sh team --apply --with-probe
RFA_HOST_IP=<호스트 IP> ./scripts/verify_policy.sh team
```

> 💡 `scripts/apply_policies.sh`와 `verify_policy.sh`는 공개 쪽 샌드박스용 정책(`rfa-host-services`)을 쓰게 되어 있다. 3-5에서 `team`용 정책 파일을 새로 쓰고 스크립트가 그것을 읽게 고쳐야 한다.

> 💡 호스트 IP는 WSL을 재시작하면 바뀐다. 정책에는 IP만 쓰고 `host.docker.internal`은 쓰지 않는다 ([nemoclaw/03-policy-verification.md](nemoclaw/03-policy-verification.md) 5절).

### 6. M4 세부 계획: 기밀 검사

| # | 할 일 | 끝났다는 기준 | 어디 | 상태 |
|---|---|---|---|---|
| 4-1 | 주고받는 형식 정하기 | 질문, 답변 원문, 걸러낸 안, 사유, 승인 표시의 형식이 문서로 있음 | 계약 | ⬜ 팀 확인 |
| 4-2 | 검열 에이전트 | 합성 원문을 넣으면 걸러낸 안과 사유(규칙 번호)를 냄 | `team` | ⬜ |
| 4-3 | 검열 결과를 호스트에 올림 | 호스트에 "기밀 검사 대기" 기록이 생김 | `team` → 호스트 | ⬜ |
| 4-4 | 기밀 검사 화면 | 원문과 걸러낸 안을 나란히 보고 승인, 고쳐서 승인, 거절 | 호스트 | ⬜ |
| 4-5 | 승인된 지식을 내보냄 | 공개 쪽이 부르는 주소가 승인된 지식만 돌려줌. 원문은 돌려주지 않음 | 호스트 | ⬜ |
| 4-6 | 경계의 코드 검사 | 승인된 지식에 비밀값과 금칙어 검사를 한 번 더 | 호스트 | ⬜ |
| 4-7 | 승인용 토큰 | 승인, 거절 요청을 출처 주소가 아니라 토큰으로 확인 | 호스트 | ⬜ |

4-1에서 정할 것:

| 항목 | 선택지 |
|---|---|
| 기록을 어디에 두는가 | RFA_module의 결재 기록에 단계를 더함 / 따로 둠 |
| `team`이 질문을 받는 방식 | `team`이 호스트에 물어봄(주기적으로) / 호스트가 `nemoclaw team agent`로 부름 |
| 승인 표시 | 승인 번호, 독자, 목적지, 기준 버전 |

4-2 구현 메모:

- 검열 기준과 과거 결정 사례는 RFA_module의 `data/policy/`에 이미 있다. 검열 노드의 프롬프트도 있다. 옮겨 와서 기밀 영역에서 돌린다.
- 확실한 검사(비밀값, 금칙어)는 코드로 먼저 돌리고, 검열 에이전트는 그 결과를 참고해 맥락 판정만 한다.

### 7. M1, M5 세부 계획: 대응 에이전트와 연결

| # | 할 일 | 끝났다는 기준 | 상태 |
|---|---|---|---|
| 5-1 | 대응 에이전트를 호스트에서 실행 | RFA_module Step 9의 방법으로 질문 1건이 결재 대기까지 감 | ✅ 승희 님 확인 |
| 5-2 | 작성, 편집, 검열 노드를 다듬기 하나로 | 워크플로가 받은 지식을 다듬기만 함 | ⬜ 승희 님과 |
| 5-3 | 업무 고르기를 head agent로 | 공개 쪽 워크플로가 업무를 고르지 않음 | ⬜ 팀 확인 |
| 5-4 | 승인 표시 확인 | 표시가 없는 지식은 받지 않음 | ⬜ |
| 5-5 | 한 바퀴 | 질문 1건이 기밀 영역, 기밀 검사, 대응 에이전트를 거쳐 게시까지 | ⬜ |

5-2와 5-3을 마감 전에 못 하면 지금의 워크플로를 그대로 쓴다. 받는 지식이 이미 승인된 것이면 남아 있는 검열 노드는 두 번째 검사로 돈다.

### 8. M6 세부 계획: 시연

| # | 장면 | 끝났다는 기준 | 상태 |
|---|---|---|---|
| 6-1 | 정상 흐름 | 시험용 레포의 멘션 → 기밀 검사에서 승인 → GitHub에 답글 | ⬜ |
| 6-2 | 기밀 차단 | 미공개 일정, 내부 주소, 토큰이 든 원문이 기밀 검사 화면에서 걸러진 것이 보임 | ⬜ |
| 6-3 | 공격: 밖으로 보내기 | `team`에서 임의 주소로 전송 → 차단, 로그에 DENIED | ✅ 옛 샌드박스에서 확인. `team`에서 다시 |
| 6-4 | 공격: 승인 호출 | `team`에서 승인 주소 호출 → 403, 로그에 DENIED | ✅ 위와 같음 |
| 6-5 | 공격: 질문 속 지시 | "내부 노트를 붙여라"는 질문 → 게시된 글에 내부 내용 없음 | ⬜ |
| 6-6 | 기록 | 각 장면의 화면과 로그를 저장 | ⬜ |

| 온보딩 실패 | 오늘 오류를 여러 번 만남 | 샌드박스를 시연 전날 확정하고 건드리지 않음 |
